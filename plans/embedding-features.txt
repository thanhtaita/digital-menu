BUILD TWO INTERCONNECTED SERVICES FOR RESTAURANT RECOMMENDATIONS

OVERVIEW:
You're building a semantic recommendation system for restaurants.
Service 1: FastAPI Embedding Server (NEW) - Generates embeddings
Service 2: Existing Fastify API - Uses embeddings for recommendations

===========================================
SERVICE 1: FASTAPI EMBEDDING SERVER (NEW)
===========================================

PURPOSE:
A dedicated service that generates and manages embeddings for dishes and user preferences.
It will regularly pull data that hasn't been embedded yet and process it.

KEY CAPABILITIES:

1. DISH EMBEDDING PIPELINE
   - Pull all dishes from the database that don't have embeddings yet
   - For each dish, combine relevant fields into meaningful text
     (e.g., name, description, category, price, dietary info should be combined intelligently)
   - Send that combined text to the Ollama model at http://localhost:11434/api/embed
   - Store the resulting vector in the database
   - Keep track of which dishes have been embedded and when

2. USER PREFERENCE EMBEDDING PIPELINE
   - Pull user preferences (long text descriptions of what they like)
   - Send the text to Ollama embedding model
   - Store the vector in the database
   - Handle updates when users modify their preferences

3. EMBEDDING METADATA TRACKING
   - Create a meta table to track embedding jobs/history:
     * What was embedded (dish or preference)
     * When it was embedded
     * Which embedding model was used
     * Success/failure status
   - This helps with debugging and auditing

4. BATCH PROCESSING
   - Should efficiently handle embedding multiple items at once
   - Should handle failures gracefully (retry, log, continue)
   - Should not overload Ollama with too many requests

API ENDPOINTS (general, not specific):
- Endpoint to trigger embedding all unembedded dishes
- Endpoint to trigger embedding user preferences
- Endpoint to check embedding status/history
- Health check endpoint to verify Ollama connection

DESIGN PRINCIPLES:
- Keep this service focused only on embeddings
- Make it loosely coupled (can run independently)
- Use the Ollama API efficiently
- Store metadata for monitoring and debugging

===========================================
SERVICE 2: FASTIFY API ENHANCEMENTS (EXISTING)
===========================================

PURPOSE:
Add recommendation features to your existing Fastify API using the embeddings
generated by the embedding server.

KEY CAPABILITIES:

1. RECOMMENDATION GENERATION
   - Accept a user preference (or fetch stored preference)
   - Retrieve that user's preference embedding from database
   - Query against all dish embeddings to find similar ones
   - Use similarity scoring to rank dishes
   - Apply filters if needed (dietary, price, restaurant, etc.)

2. SIMILARITY MATCHING LOGIC
   - Compare user preference embedding with each dish embedding
   - Use cosine similarity to find how "close" they match
   - Return dishes ranked by similarity score

3. RANKING & STORAGE
   - Store the recommendations shown to users
   - Track which recommendations the user interacted with (clicked, selected, etc.)
   - This creates a history of recommendations for analytics

4. USER ENGAGEMENT TRACKING
   - Record when users see recommendations
   - Record when they click or select a dish
   - This data helps improve recommendations over time

API ENDPOINTS (general, not specific):
- Endpoint to generate recommendations for a user
- Endpoint to get a user's stored preferences
- Endpoint to submit feedback on recommendations
- Endpoint to view recommendation history

DESIGN PRINCIPLES:
- Use pgvector's built-in similarity functions
- Cache recommendations if they don't change often
- Track engagement for future improvements
- Make it easy for frontend to consume

===========================================
DATABASE ARCHITECTURE
===========================================

TABLES involved
- dishes (dish details)
- user_preferences (user preference text)
- dish_embeddings (vectors for dishes)
- user_preference_embeddings (vectors for preferences)
- embedding_jobs or embedding_history
  Records: what was embedded, when, status, model used
- recommendations (user → dish matches)
  Records: who saw what recommendation, ranking score
- recommendation_feedback (user interactions)
  Records: clicks, selections, timestamps

===========================================
DATA FLOW
===========================================

FLOW 1: INITIAL EMBEDDING (FastAPI Server)
1. FastAPI checks for unembedded dishes
2. Reads dish records from database
3. Intelligently combines dish fields into text
4. Sends text to Ollama
5. Stores embedding vector in dish_embeddings
6. Records in embedding_jobs meta table

FLOW 2: PREFERENCE EMBEDDING (FastAPI Server)
1. FastAPI checks for unembedded user preferences
2. Reads preference text from database
3. Sends text to Ollama
4. Stores embedding vector in user_preference_embeddings
5. Records in embedding_jobs meta table

FLOW 3: RECOMMENDATION (Fastify Server)
1. User asks for recommendations
2. Fastify retrieves user's preference embedding
3. Uses pgvector to find similar dish embeddings
4. Sorts by similarity score
5. Applies filters and ranking logic
6. Stores the recommendations in recommendations table
7. Returns ranked dishes to user

FLOW 4: USER FEEDBACK (Fastify Server)
1. User clicks or selects a recommendation
2. Fastify records this in recommendation_feedback table
3. This data becomes training signal for future recommendations

===========================================
IMPLEMENTATION APPROACH
===========================================

START WITH:
1. FastAPI Embedding Server
   - Set up basic FastAPI app
   - Connect to PostgreSQL
   - Connect to Ollama
   - Create services for embedding dishes and preferences
   - Add meta table for tracking
   - Create endpoints to trigger embedding jobs
   - Test with sample data

2. Fastify API Enhancements
   - Add services for recommendation logic
   - Implement similarity search queries
   - Create APIs for getting recommendations
   - Create APIs for storing user feedback
   - Add tables for tracking recommendations

KEY CONSIDERATIONS:
- Text combination strategy matters (how you format dish data affects embedding quality)
- Batch processing improves efficiency
- Error handling and retries are important (embedding can fail)
- Metadata tracking helps with debugging
- Engagement tracking enables future improvements
- Both services should be independently deployable

===========================================
TECHNOLOGY STACK
===========================================

FastAPI Embedding Server:
- FastAPI (Python web framework)
- psycopg2 (PostgreSQL driver)
- httpx or requests (HTTP client for Ollama)
- pgvector (for vector storage)

Fastify API (existing, add to):
- Fastify (Node.js framework)
- pg (PostgreSQL driver)
- Services for recommendation logic

===========================================
ENVIRONMENT & SETUP
===========================================

FastAPI Server connects to:
- PostgreSQL (same database as Fastify)
- Ollama at http://localhost:11434

Fastify Server connects to:
- PostgreSQL (same database as FastAPI)
- Optionally calls FastAPI embedding endpoints

Both run independently but share the same PostgreSQL database.
